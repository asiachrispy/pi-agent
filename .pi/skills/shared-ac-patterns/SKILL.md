# shared-ac-patterns

验收标准（AC）是 PRD 中唯一机器可读、可自动化验证的部分。AC 质量直接决定 QA 自动化上限。

## 强制规则

- AC 必须按 `AC-001`、`AC-002`、`AC-003` 编号，编号在 PRD 内递增且连续。
- 每条 AC 必须可测试，描述必须包含三要素：
  - **前置（Given）**：测试开始时的状态或数据。
  - **动作（When）**：用户或系统执行的操作。
  - **断言（Then）**：期望结果或系统响应。
- 至少包含三类 AC：
  - **正向**：主流程成功路径。
  - **反向**：权限不足、数据为空、参数非法等失败路径。
  - **边界**：极端数据、并发、跨日 / 跨时区等。

## 标准模板

```text
[AC-001] 给定 <前置状态>，当 <触发动作>，则 <期望结果>。
[AC-002] 给定 <角色 X>，当 <执行操作 Y>，则 <结果或提示 Z>。
[AC-003] 给定 <空数据 / 异常输入>，当 <触发动作>，则 <错误提示或兜底>。
```

## 范例

```text
[AC-001] 给定采购主管选择 1-50 条待审核采购单，当点击批量审核，则系统批量审核成功并提示"已审核 N 条"。

[AC-002] 给定采购员（非采购主管），当尝试批量审核，则系统提示"无操作权限"且不改变状态。

[AC-003] 给定选择 51 条采购单，当点击批量审核，则系统提示"单次最多支持 50 条"且不改变任何状态。

[AC-004] 给定批量审核过程中后端接口超时，当重试，则系统按幂等规则保证不重复审核。

[AC-005] 给定审核成功后状态为"已审核"，当查询列表，则列表实时显示"已审核"状态。
```

## 反例

以下写法禁止使用：

```text
✗ [AC-001] 系统应该支持批量审核。
✗ [AC-002] 性能要好。
✗ [AC-003] UI 要美观。
```

原因：不可测试、不可自动化、不可验收。

### ERP 场景专项反例

以下写法在 ERP 上下文尤其容易踩坑，虽然看似具体，但测的是实现而非行为：

```text
✗ [AC-001] 系统用 Redis 缓存采购单列表，缓存 Key 为 purchase:list:{userId}。
→ 问题：暴露了缓存选型（Redis）和 Key 命名，这些是内部实现细节。
→ 正确：给定已查询过采购单列表，当再次查询同条件，则第 2 次返回 < 100ms。

✗ [AC-002] 批量审核通过后发 MQ 消息给 WMS 模块切发货单。
→ 问题：暴露了通信方式（MQ）和目标模块名。模块名可能重构，MQ 可能换。
→ 正确：给定批量审核成功，当 WMS 模块收到通知，则生成对应发货计划。

✗ [AC-003] 后端 Controller 调用 SharedService，SharedService 注入 PMS Mapper 查采购单。
→ 问题：暴露了调用链（Controller→SharedService→Mapper）。内部重构时 AC 会误报失败。
→ 正确：给定需要跨模块查询采购单，当调用约定的跨模块接口，则返回正确的采购单数据。
```

## 行为级自检清单

每条 AC 写完必须通过以下 3 项自检：

- [ ] AC 描述的是用户 / 调用方可观察的行为，不是代码内部如何实现
- [ ] 重命名接口路径、换掉缓存方案、改 MQ topic 名后，AC 仍然成立
- [ ] AC 断言的是结果或系统响应（如"返回 X""提示 Y"），不是中间步骤（如"先查数据库""再推队列"）

反模式速查：

| 如果你的 AC 里出现... | 很可能在测实现 |
|---|---|
| 缓存（Redis / Ehcache / Caffeine） | 改成"第 N 次查询 ≤ X ms" |
| MQ / Kafka / RocketMQ | 改成"消费者收到通知后 Y 发生" |
| Controller / Service / Mapper / Repository | 改成"调用约定接口返回 Z" |
| 具体的模块名或项目名 | 改成"下游模块"或"对应系统" |

## 与 DoR 的关系

- PRD 中 AC 总数 ≥ 3 才满足 Definition of Ready。
- AC 中必须出现至少 1 条反向用例。

## 在各 agent 中的使用

| agent | 使用方式 |
|---|---|
| `/team` | 生成 PRD 时按本 skill 写 AC，并 review 自身输出 |
| `/team` | 实现完成后输出 `ac_coverage: N/M`，列出每条 AC 是否实现 |
| `/team` | 按 AC 编号逐条验收，输出 `prd_ac_passed`、`prd_ac_failed` |
| `/team` | 检查每条 AC 在代码 diff 中是否有对应实现 |

## 维护规则

- 新增 AC 模式时，必须更新本 skill 的范例区。
- AC 编号在 PRD 内重新编号，不跨 PRD 复用。
